Structure. Momentum. Independence.

Before we dive in, we have 3 beliefs and limits at Learn to Cloud that dictate what we build and more importantly, what we don't build.

First, we're primarily two core contributors doing this in our free time. We're building and maintaining the platform, responding to bugs, and following up with learners on Discord and GitHub Discussions.

Second, we don't monetize Learn to Cloud. If students spend money, it goes directly to authors for recommended learning materials or to cloud providers for services in their own accounts. None of it comes to us. So keeping the platform inexpensive to run is what makes it possible for us to keep doing this.

And third, technical skills aren't the only thing we want learners to leave with. Our curriculum needs to give them structure, momentum, independence.

Structure

Structure through
real work.

Learn→Do→Verify

Like I mentioned, structure is one of the things we're engineering for. We don't want to give learners a list of resources and say, "Good luck becoming a cloud engineer."

That's why the curriculum is phase-based, with each phase building on the previous one. Learners get material to study, hands-on work to complete, and a way to verify that work before moving forward.

And we want that hands-on work to look like what they'll actually do as engineers, not just exercises inside our platform.

This is where GitHub becomes more than our login button.

Phase 0 / Repositories / Structure

A first real workflow.

Create→Clone→Change→Push

Right from Phase 0, learners are creating a repository, cloning it, making changes, and pushing those changes back to GitHub.

These are small tasks, but they're not throwaway exercises. They're steps learners will repeat throughout the curriculum and in real projects.

Independence / Lab scenario

Why can't these talk?

Frontend✕Backend

Investigate. Verify. Clean up.

In the networking lab, for example, they might have a frontend that can't reach its backend.

We give them the scenario and the resources to investigate. They use shell commands, read documentation, change configuration, and check whether it worked.

This is where independence comes in. We want to give them enough structure to know what they're trying to accomplish, without giving them every step of the solution.

When they finish, they submit a completion token that our platform verifies. They can get recognition for the work without waiting for one of us to review it.

And then they clean up. These are real resources that cost money. Knowing what you deployed, and confirming that you removed it, is part of the work too.

Phase 3 / Pull requests / Structure

Build with a process.

01 Branch

02 Implement

03 Open a PR

04 Add a label

05 Investigate

By Phase 3, learners are building a journal API with Python, FastAPI, PostgreSQL, and AI-powered analysis.

That's a bigger assignment. "Build this application, then come back when you're done" isn't enough structure.

So we break the project into assignments, and those assignments follow a real development workflow.

They fork the starter repository, clone it, and open the provided development container. Then, for each assignment: branch, implement, open a PR, add a task label, investigate checks, review and merge.

The GitHub features here are pull requests, labels, and Actions. But what they give the learner is a repeatable process.

Here's the change you're making. Here's where you can review it. Here's the feedback on whether it behaves as expected.

They came to learn Python. They're also practicing how to work in an existing codebase, make focused changes, and use automated checks.

We almost built an AI grader for this. Our first thought was an agent framework and agents reviewing the code. Then we stepped back: for these requirements, we can describe the expected behavior with tests and run them with GitHub Actions.

That gives learners a concrete target and feedback they can act on.

At the end, the capstone workflow runs the full test suite and checks linting, formatting, and types. Our app confirms that it passed for the current commit on main.

The requirements and workflow give them structure. Passing checkpoints gives them momentum. Working through failures builds independence.

GitHub Releases / Maintenance + cost

Deliver the labs.
Not the machines.

We want learners working with real infrastructure. We don't want to operate a separate lab environment for every learner.

Our approach is to maintain and distribute the lab code, while learners run it in their own accounts.

For the Linux lab, GitHub Actions packages the setup code from a release tag and publishes it through GitHub Releases, alongside a checksum: linux-ctfs-setup.tar.gz and linux-ctfs-setup.tar.gz.sha256.

Learner deployments download that package. GitHub Releases gives us a place to distribute it without building a separate delivery system.

This doesn't make the learner's infrastructure free. It keeps that infrastructure in their control, and keeps us from having to host everyone's machines.

That's the cost constraint shaping the architecture, without turning the hands-on work into a simulation.

GitHub Copilot / Lab maintenance

Don't fix
the assignment.

Preserve intentional misconfigurations.

Copilot reports. We decide.

Distributing the labs is one part. Keeping them usable is another.

We spent weeks creating the Linux and networking exercises from our own experience. But Terraform providers, cloud CLIs, and dependencies keep changing after we've written the lab.

That's where we use GitHub Copilot: helping maintain the exercises, not deciding what they should teach.

There's a catch with the networking lab. Broken infrastructure is the assignment.

I don't want Copilot "helping" by fixing the problem the learner is supposed to solve.

So our maintenance skill says: Preserve intentional misconfigurations. Establish each incident's intended fault from the guides and implementation before flagging it as a problem.

Copilot checks the implementation and instructions against current official documentation. It reports problems and identifies what still needs live verification.

That review doesn't change code or cloud resources. We decide what to fix.

For us, that helps with maintenance. For learners, the distinction matters: we want them troubleshooting the intended challenge, not an outdated instruction we accidentally left behind.

"What do I do next?"

Our dog-food agent: use the app, report the evidence.

On the app side, a lot of our code is AI-assisted. Copilot helps us implement changes under our repository instructions and validation checks.

But passing tests doesn't tell us whether a learner knows what to do next.

A page can load perfectly and still be confusing.

And if we're engineering for momentum and independence, that confusion matters. A learner shouldn't need to ask us on Discord just to find out how to submit their work.

So we also have a custom dog-food agent that uses the local app through a browser, with a goal like submitting the Phase 3 requirement.

It follows the links the page actually offers. It distinguishes defects from friction: a server error is one kind of problem; a message that leaves you guessing is another.

It reports findings with evidence and says what it didn't exercise, rather than quietly fixing things.

That doesn't replace learner feedback. It gives two maintainers another way to catch problems before learners encounter them.

The goal is for learners to need us less

At the beginning, I said we're building around a few constraints and beliefs.

We have limited time. The platform needs to stay inexpensive to run. And learners need more than technical content: they need structure, momentum, and independence.

Those are what drive our choices.

GitHub isn't just where we store the code. It's where learners take their first steps, build projects, and learn to work through feedback. It also gives us tools to distribute and maintain that experience without building everything ourselves.

The goal isn't to remove every difficulty. Investigating a failed test or troubleshooting a network is part of learning.

The goal is to remove the unnecessary waiting and confusion around that work.

Less time waiting for us to approve a checkpoint. More confidence taking the next step.

Eventually, we want learners to need us less, not because we've stopped supporting them, but because they know how to keep going.
